# Mio 연속 대화 목업 · 기획/FE/LLM 인수인계

상세 생성 원칙·BE/FE 계약: [BACKEND_LLM_CONVERSATION_POLICY.md](BACKEND_LLM_CONVERSATION_POLICY.md).

8개 시나리오 × 4쌍 = 32쌍(64개 메시지). 기존 단일 톤 예시 5쌍은 별도로 유지한다.

**전부 창작한 기획 데이터다. 실제 잠재 고객·상담사 인터뷰 인용, LLM 출력, 상담사 감수 결과, 치료 효과 자료 또는 학습 데이터가 아니다.** 사례 속 사용자의 평가 역시 의도적으로 작성한 대사이지 관측값이 아니다.

## 왜 이 정도인가

반복적인 위로를 많이 만드는 대신, 실제 필요한 응답 전환을 검토할 8개 상황을 선택했다. 경청에서 멈추기, 허락 후 정리, 사실/추측 구분, 오해 수정, 도움이 없다는 평가, 대화 부담과 중단, 전문 상담 탐색, 기존 대안의 충분함을 다룬다. 각 사례의 첫 발언부터 마지막 평가까지 4쌍으로 이어진다. 현재 필요는 학습용 데이터 대량 생산이 아니라 기획 의도·UI 상태·LLM 응답 기준의 합의다.

## 역할과 전달 범위

| 담당 | 전달/구현 범위 |
|---|---|
| 김종혁 · 기획/UIUX | 화면 퍼블리싱, 창작 대화/기대 응답, 문구/선택/예외 상태, 최소한의 로컬 수정·초기화 |
| 지정 FE 담당 | API 계약에 맞는 화면 연결, 스트리밍/중단/재시도, 상태 유지/최적화, 접근성·모바일 검증 |
| 효찬 · BE/LLM | 실제 모델 연동, 동의 검증·저장·철회, 데이터 처리/보존, 응답 정책·안전 체계, 인증·서버 이벤트 |

새 인원은 현재 작업 담당자로 추가하지 않았다. 상담사 인터뷰와 잠재 고객 인터뷰를 병행한다는 계획은 실제 감수/검증 완료와 다르다. 모집·연락·배포·push는 이번 작업에서 수행하지 않았다.

## 앱에서 확인

1. 홈 → 동의 → 원하는 도움 → 대화.
2. 입력창 위 **다른 대화 상황 보기**를 열고 상황을 고른다. 선택하면 이전 대화와 정리는 초기화된다.
3. **이 이야기로 시작하기 / 이어서 이야기하기**를 누르면 다음 가상 사용자 문장이 입력창에 들어간다. 보내기를 눌러야 전송 동작이 시작된다.
4. 답변이 끝나야 다음 예시로 넘어간다. 실패·중단은 단계를 소비하지 않는다. 화면을 나갔다 돌아와도 완료된 단계는 유지하고, 미완성 응답을 다시 표시할 때 사용자 문장을 중복 추가하지 않는다.
5. wait/pause에서는 다음 예시가 숨겨진다. “내가 더 이야기할게요”를 눌러야 예시가 다시 열린다. end에서는 “여기서 마치기”로 평가/인터뷰 없이 종료한다.
6. 정리에서는 같은 사례의 현재까지 나온 사용자 발언에 해당하는 누적 샘플만 보여준다. 미래 발언의 감정·결과를 앞당겨 쓰지 않는다.
7. `/tone-guide`에서 모든 대사·설계 의도·피할 응답을 확인한다. 사용자 메뉴에는 팀용 링크를 노출하지 않는다(`?internal=1`에서만 링크 노출; 인증 수단 아님).

## 파일/API 연결 기준

- `src/lib/conversation-scenarios.json`: UI와 문서의 공통 원본. scenario `id/title/need/description/outcome/turns`; 각 turn `id/user/reply/principle/avoid/summary/followUp`.
- `outcome/principle/avoid`는 팀용 설명. 대화창에는 `user/reply`만 표시한다.
- `fixtureId`는 공개 창작 문장의 고정 ID. 고객 ID나 실제 원문을 이벤트에 넣지 않는다.
- `nextScenarioTurn()`은 완료된 `source=mock` 답변 ID로 진도를 계산한다. 자유 입력은 순서를 진행시키지 않는다.
- `scenario_selected`와 `mock_fixture_sent`의 `resource`는 고정 시나리오/턴 ID. 실제 대화·도움·자기노출로 집계하지 않는다. 기존 v5.2 로컬 기록만 사용하며 서버 호출은 없다.
- 정리는 `source=fixture`와 정확한 ID/문장 및 앞 단계 존재를 확인한다. 자유 입력이나 미래 단계는 집계하지 않는다. 수정한 정리는 사용자가 직접 내려받을 때만 파일에 포함된다.
- LLM 연동 시 목업 `fixtureId`를 실제 모델 답변에 붙여 성공한 시나리오처럼 기록하지 않는다. 별도 `live` 모드/모델 응답 식별자/동의 버전/서버 측 권한 계약이 필요하다.

## 공통 응답 기준

- 짧은 해요체를 기본으로 하되 무조건 같은 길이/질문 수를 강제하지 않는다.
- 사용자가 말한 사실·감정과 AI 추측을 구분한다. 감정을 말하지 않았으면 요약에 추가하지 않는다.
- 감정에 공감하는 것과 타인 비난·사용자 판단에 동의하는 것을 구분한다.
- 정리/조언 전 필요한 도움을 확인한다. 경청만 원하면 숙제를 주지 않는다.
- 오해를 지적받으면 수정한다. `correct_me`는 자기평가에 대한 잠정적 확인이 어긋난 뒤 사용자가 바로잡는 사례다. 말하지 않은 불안을 먼저 추정하지 않는다.
- 도움이 없다는 평가를 성공으로 재해석하지 않는다. 부정/혼합 경험을 그대로 보존한다.
- 종료 요청에는 질문·정리·재방문 요구를 붙이지 않는다. 실제 UI의 마무리는 항상 이용 가능하다.
- 전문 도움 탐색은 선택으로 열어두되 진단·예약·연결 완료·치료 효과를 주장하지 않는다.
- 친밀감이나 데이터량을 높이려고 지인/전문가와의 관계를 대체하거나 원문 공개를 유도하지 않는다.

## 도움 검증과 목업 평가의 구분

목업을 본 사람에게는 “이 답변에서 맞게 짚은 점/어긋난 점은 무엇인가요?”, “질문·조언·정리 중 부담스러운 부분이 있나요?”, “이 상황에서 실제로 필요할 도움은 무엇인가요?”를 묻는다. 타인이 쓴 사례에 대한 평가는 개인이 실제 도움을 받았다는 증거가 아니다.

실제 LLM 관찰에서는 별도 동의와 운영 준비 후, 이해의 정확성·필요와의 적합성·도움 없음·오히려 불편함·기존 대안 대비 선택·이후 실제 행동을 나누어 기록한다. 과제 생성은 실행이 아니고, 정보 열람은 상담 이용이 아니다. 사용자 자기보고도 임상 효과와 구분한다.

## 현재 빠진 범위

이 자료에는 즉각적 자해·타해 위험, 미성년자 특화 대응, 약물/진단 질문, 학대/응급 상황, 다국어 등 전반적 안전 평가 세트가 없다. 자유 입력의 의미 분석이나 위험 탐지는 전혀 구현하지 않았다. 8개 예시를 통과했다고 LLM의 안전성·효능이 검증되는 것은 아니다. 실제 서비스로 전환할 때 BE/LLM와 상담사 검토로 별도 다룰 범위다.

## 시나리오 목록

- **퇴근해도 일이 머릿속에 남을 때** (`after_work`): 부분적 도움: 말할 부담은 줄지만 상황은 그대로
- **무엇부터 해야 할지 막막할 때** (`too_many_tasks`): 실용적 도움 후보: 정리했지만 실제 실행은 미확인
- **답장이 늦어 여러 생각이 들 때** (`late_reply`): 부분적 도움: 단정은 줄었으나 불안은 남음
- **내 말을 잘못 이해했을 때** (`correct_me`): 수정 후 제한적 도움: 이해받았다는 응답만 확인
- **좋은 말인데 도움이 안 될 때** (`not_helping`): 도움 없음: 구체적 판단에 필요한 정보 부족
- **이야기할수록 더 힘들 때** (`too_much`): 부정 경험과 중단: 추가 자기노출을 유도하지 않음
- **전문 상담을 받아야 할지 고민될 때** (`professional_help`): 정보 탐색 선택: 상담 이용·예약은 미확인
- **기존 방법이 더 잘 맞을 때** (`existing_method`): 대안 충분: Mio 필요와 재사용을 가정하지 않음
